# Requirements Quality Checklist: Generic Research Control and Binding

## Completeness

- [x] CHK-001 Every user story has a priority and an independent test.
- [x] CHK-002 Every user story has at least one concrete acceptance scenario.
- [x] CHK-003 Functional requirements are uniquely identified from FR-001 through FR-014.
- [x] CHK-004 Success criteria are measurable and limited to buildable outcomes.

## Consistency and boundaries

- [x] CHK-005 The generic preset is explicitly prohibited from binding a concrete Skill, tool, dataset, or project path.
- [x] CHK-006 Plan-time capability selection is distinct from task-time execution binding.
- [x] CHK-007 Skill and Extension responsibilities are stated without making either a lifecycle stage.
- [x] CHK-008 The six core and three optional commands are classified without claiming a universal official nine-stage taxonomy.
- [x] CHK-009 Personal phase labels and external review/score/repair/test facilities are explicitly out of the core scope.
- [x] CHK-010 Existing non-`bio-*` identifiers are explicitly preserved for this feature.

## Failure and evidence behavior

- [x] CHK-011 Missing or ambiguous capability metadata has an explicit fail-closed or blocked outcome.
- [x] CHK-012 Provenance requirements identify the selected source/version, parameters, and artifacts.
- [x] CHK-013 Concrete MultiQC execution is separated from the generic control workflow.
- [x] CHK-014 Each research acceptance criterion names an evidence artifact or validation command and a failure action.

## Scope discipline

- [x] CHK-015 The feature does not require real biological data or claim biological validity.
- [x] CHK-016 The historical `01-spec-work-package` is preserved rather than silently rewritten.
- [x] CHK-017 No requirement introduces a second canonical name for `spec.md`, `plan.md`, or `tasks.md`.
